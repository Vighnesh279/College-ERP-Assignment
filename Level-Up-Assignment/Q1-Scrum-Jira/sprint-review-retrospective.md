\# Q1 — Sprint Review and Retrospective



\## 1. Project Details



\*\*Project:\*\* College ERP System  

\*\*Sprint:\*\* College ERP Sprint 1  

\*\*Scenario:\*\* Student login and access to academic information



This document records a simulated Sprint Review and Sprint Retrospective for the academic Scrum exercise. The feedback and meeting outcomes below are scenario-based and should not be interpreted as evidence of a meeting with real stakeholders.



\## 2. Sprint Review



\### Objective



To review the planned College ERP user stories against their acceptance criteria and obtain stakeholder feedback.



\### Participants and Roles



\- \*\*Product Owner:\*\* Simulated student representative

\- \*\*Scrum Master:\*\* Student project coordinator

\- \*\*Development Team:\*\* Student developer and tester



\### Product Backlog Items Reviewed



1\. Student Login to College ERP

2\. View Academic Dashboard

3\. View Student Attendance

4\. View Examination Results



\### Review Findings



The team reviewed the acceptance criteria and supporting tasks for all four user stories. Login validation, dashboard navigation, attendance display, and examination-results access were identified as the main areas of planned work.



At the time of this review, the login test-planning task had been moved to In Progress, while the remaining supporting tasks were still planned work. A fully implemented College ERP application has not yet been demonstrated.



\### Simulated Stakeholder Feedback



The simulated Product Owner provided the following feedback:



\- Login errors should be clear and understandable.

\- The dashboard should provide direct access to attendance and examination results.

\- Students must not be able to view another student's private academic records.

\- Missing or unpublished information should be communicated clearly.



\### Product Backlog Updates



The team will refine the login validation and access-control requirements. Additional test cases will be prepared for invalid credentials, unauthorized access, missing attendance data, and unpublished examination results.



\### Review Outcome



The review identified useful refinements to the Product Backlog. The application increment and its acceptance criteria must be verified before the related stories can be considered complete.



\## 3. Sprint Retrospective



\### What Went Well



\- User stories were created with acceptance criteria.

\- The Product Backlog was prioritized.

\- Supporting tasks were created for the main student features.

\- Story-point estimates were recorded.

\- A Daily Scrum discussion was documented in Jira.



\### Challenges Identified



\- Authentication and authorization requirements need careful validation.

\- The stories cover several distinct features and require manageable tasks.

\- The planned functionality still needs an implemented increment and testing evidence.



\### Improvement Actions



1\. Clarify authentication rules before implementation.

2\. Divide larger features into small, verifiable tasks.

3\. Prepare test cases alongside implementation work.

4\. Review acceptance criteria during development rather than only at the end.

5\. Record requirement changes in Jira and reprioritize the Product Backlog when necessary.



\## 4. Scrum Artifacts



\- \*\*Product Backlog:\*\* The four prioritized College ERP user stories.

\- \*\*Sprint Backlog:\*\* The sprint plan, story-point estimates, supporting tasks, and proposed timelines.

\- \*\*Increment:\*\* The working functionality demonstrated during the sprint. This must be created and tested before claiming the planned features are implemented.



\## 5. Conclusion



The simulated Sprint Review and Retrospective demonstrate how Scrum can support requirement clarification, feedback, and continuous improvement. The Jira backlog and board provide a way to track planned work. The next step is to implement a small working increment and check it against the acceptance criteria before recording implementation as complete.
